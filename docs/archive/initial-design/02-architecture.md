# Architecture

*Updated after the spikes ([results](07-spike-results.md)): the UI bridge, the text-file overlay and a chat-based
channel are confirmed on 3.29.3d. The loader is still untested.*

## Principles

1. **Mods stay server C#.** The server is authoritative in this game and LocalExile's mods already hot-reload. A mod
   author writes C# and ships data (`.ui` files, images, table rows). No mod ships native code.
2. **One trusted client component.** The client host is written once, reviewed once, and shipped by LocalExile. It
   is generic: it knows nothing about any mod, league or module, the same rule the framework follows on the server.
3. **Nothing on disk is rewritten.** No bundle, index or GGPK write. Mod files are overlaid in memory. The only
   on-disk change is in the copy LocalExile already generates, `Game.patched.exe`.
4. **Opt-in and removable.** Without the host the client is exactly today's client, and a mod that wants the host
   can tell it is missing and fall back to chat.
5. **Two builds, fixed addresses.** 3.29.3c and 3.29.3d only.

## Overview

```
 Waypoint ──installs──▶ Mods/Binaries/<id>/      server mod (C#, as today)
                        Mods/Client/<id>/        client payload: .ui, images, table patches   (new)

 LocalExile patch step ──▶ Client/Game.patched.exe  (+ one import: the client host)          (new, opt-in)

 ┌──────────────── client process ────────────────┐         ┌──────────── Gateway ────────────┐
 │  client host (DLL)                             │         │  ClientHost framework service   │
```

## 1. Loading the host

**Choice: add an import to `Game.patched.exe`.** `GameServer.Auth patch` already writes that file from `Game.exe`
(login keys, `LooseFilesPatch`). One more optional step appends an import-table entry for
`LocalExile.ClientHost.dll`, so Windows' loader, and Wine's, map the host before the entry point runs. No injector,
no environment variable, no difference between Windows and Proton.

| Alternative | Why not first |
|---|---|
| Proxy DLL (`version.dll` beside the exe) | Needs no exe change, and is the fallback. Under Wine it also needs `WINEDLLOVERRIDES=version=n,b`, which every launcher path (`live.ps1`, `LocalExile`, Waypoint, a user's runner) would have to set |
| Suspended spawn plus injection | Works on Windows (`nullifier.py` does it with Frida). A native Linux launcher cannot do it to a Wine process |
| Frida gadget as the host | Fast to write and matches the existing scripts, but adds a 20 MB+ dependency and a JavaScript runtime on the game thread. Good for the spikes, not for the product |

The host is a small C++ DLL: a hook library (MinHook or equivalent), the address table, and the services below. It
starts nothing until the engine reaches a known point (the state-stack update `0x141528fbf`, the frame point
`client-control.js` already uses), so all its work runs on the game thread.

**Policy:** this touches the patch step and the launch rules, so it is a maintainer decision
([roadmap](06-roadmap.md), "Open decisions").

## 2. Two builds

The host carries a table per build: each entry is a name, an address, and the expected bytes at that address. On
start it identifies the build (the same SHA-256 LocalExile uses, or the bytes at a known site) and refuses to
install any hook whose bytes differ, the rule `checked()` and `globalAt()` follow in `nullifier.js`. Code addresses
are shared between c and d; globals and vtables get one value per build, generated by
`scripts/re/port/compare_builds.py --data-map`. With no third build to chase, there is no signature scanner to
write or maintain.

## 3. File overlay

Mods need files the client does not have: `.ui` layouts, images, changed or new table rows, strings.

**Layout on disk**

```
Mods/Client/<id>/
  files/                    paths as the client names them, lower case
    metadata/ui/mods/<id>/garden.ui
    art/2dart/uiimages/mods/<id>/panel.dds
  tables/                   row patches, not whole tables (see tooling)
    baseitemtypes.json
```

**Two ways to serve them, to be decided by spike 3:**

- **A. Hook the client's read.** Confirmed for text files: after the stream open `0x1421d5b50`, swap the buffer for
  the overlay's file. The general form is the same swap one level down, in the whole-file read `0x140e564d0`, which
  every format goes through; that level is not yet tested. Cleanest, and reloads per file.
- **B. A merged index beside the real one.** Waypoint (or the host at start) writes a merged copy of
  `_.index.bin` plus one mod bundle into a cache folder outside `Client/`, and the host redirects the client's
  `CreateFileW` for those two names. Needs only Win32 hooks, which are already proven here, plus an index and bundle
  writer (the reader exists in `GameServer.Data`). No hot reload without restarting the client. Works only for the
  loose (`Bundles2`) layout; a GGPK install would need the lookup hook anyway.

A is the target and works today for layouts. B is the fallback if binary formats turn out to need the index.

**Table patches** are merged by the host (or by Waypoint into the cache) into the client's `.datc64` at load: the
mod ships rows, never GGG's file. The server applies the same rows to `client.db`/`world.db` so both sides agree
([API](03-api.md), "Registries").

## 4. Mod channel

**Version 1: chat.** The spikes showed that the existing chat messages are enough to start with, and need nothing
from the Gateway: the server sends a chat line with a reserved prefix, which the host takes before it is shown, and
the host sends a chat command back through the client's own writer. A mod reaches it with what it has today
(`conn.Commands.Reply`, `GameEvents.Command`). It is text only, as slow as chat, and shares the command namespace,
so it suits opening windows and reporting clicks, and nothing frequent.

**Version 2: a dedicated id.** One reserved S→C id and one reserved C→S id, both outside the client's range
(`≥ 0x2fc`), carrying an envelope:

```
u16 id (reserved)   u16 channel   u32 length   payload
```

- **S→C:** the host hooks the dispatcher `0x142150ae0` (or the reader that feeds it) and consumes the reserved id
  before the client sees it. Because instance messages have no length prefix, the envelope's own length is what
  keeps the stream aligned.
- **C→S:** the host writes with the client's buffered writer under the socket lock, exactly as
  `client-control.js` does; the encryption stays the client's.
- **Gateway:** a general envelope reader for the reserved id, exposed as a framework hand-over
  (`GameEvents.ClientMessage(channel)`), naming no mod.
- **Channels:** channel 0 is the host's own (handshake, UI bridge, file sync); a mod gets a channel by name hash.

**Handshake.** On every area connection the host sends its version, the client build and the list of client
payloads it loaded (id and content hash). The Gateway records `HasClientHost` and the capability set on the
connection. A mod asks before using a client feature and falls back otherwise.

Why in-band and not a side socket: ordering with game messages (open a window after the area loads, update a label
with the kill that caused it) comes for free, and there is no second connection to authenticate.

## 5. UI bridge

The host exposes the client's UI system as a small set of operations on handles:

| Operation | Client side |
|---|---|
| `open(path, parent)` | create a control, call the `.ui` loader `0x1418b08d0`, attach it under a host-owned root in the in-game state |
| `close(handle)` | detach and release |
| `find(handle, "a.b.c")` | child by `id` path |
| `set(handle, property, value)` | text, visible, enabled, position, size, progress, selected, image |
| `subscribe(handle, event)` | click, text changed, selection changed, hover, key; forwarded as a channel message |
| `confirm(title, text, buttons)` | the client's own `ConfirmationWindow` |
| `openScreen(kind, a, b, c, d)` | what S→C `0x7b` does today, for completeness |

Three rules came out of the spikes:

- **Catch everything around the loader.** A `.ui` parse error is a C++ exception that nothing in the game catches on
  this path; uncaught, it closes the client. The host catches it and reports the parser's message (it has file, line
  and column) to the server and the log.
- **One container per window.** Ids must be unique among siblings, so the host loads each mod window into its own
  container control and removes that container before loading the window again.
- **Lint before loading.** At least one valid-looking layout made the game's layout code spin forever. The host
  refuses a file the linter has not passed ([tooling](05-tooling-and-assets.md)).

Updates are batched per frame. The server never holds a pointer: handles are numbers the host maps to controls, and
a control destroyed by the client invalidates its handle with a message.

If spike 2 shows the loader cannot be used from outside, the fallback is an overlay drawn in the swap chain
(D3D11 `Present` / Vulkan), which works but does not look or behave like the game's UI.

## 6. System bridges

Later, the same handle-and-message pattern covers the other systems in [findings](01-findings.md) §2–3:
ruleset messages (send and receive for any ruleset id), object function calls (`0x285`, already server-side),
component reads, camera, sound. Each bridge is general and names no feature.

Waypoint keeps its rule of never starting the client: it only places files and flips the option; LocalExile's own
launch does the rest.

## 8. Multiplayer

A player who joins someone else's server needs the same client payloads. The handshake tells the server what each
client has; Waypoint can fetch missing payloads from the mod catalog before connecting. The patch server is a
possible second route (it already speaks the client's patch protocol) and is left for later.

## 9. Safety

- The host accepts messages only from the server the client is connected to, and LocalExile's client only connects
  to the local login list.
- UI and file operations are data. There is no "run this code" message.
- A payload is addressed by mod id under `Mods/Client/`; the overlay refuses paths that leave it.
- A mod on the server already runs with the Gateway's rights, so the client host does not widen what a mod author
  can do to the machine; it must not widen what a remote server can do to a joining player beyond drawing UI and
  loading that player's installed payloads.
